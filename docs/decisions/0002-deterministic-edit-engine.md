# ADR-0002: A deterministic edit engine, not AI-generated pixels

- **Status:** Accepted
- **Date:** 2026-08-06

## Context

"Music video generator" reads, on first hearing, like an obvious application
for a generative video model: describe a vibe, get pixels. The reference
case study this project generalizes from (`docs/case-studies/love.md`)
argues the opposite. That video is real photography — 402 photos shot by
the artist, reviewed down to 246 selects, sorted into four mood "stations"
— assembled into a beat-synced timeline with classical effects (cuts, zooms,
color grades, strobes, freezes). Nothing in it is model-generated.

The project brief this repository implements is explicit about priorities:
*"efficient token... minimal and fast... we don't wanna keep it high
quality."* A 10-minute video at even a modest frame rate is 14,000+ frames.
Per-frame (or even per-shot) generative calls for something that long are
slow, expensive, and — this is the part that matters more — throw away the
one thing that made the reference case study work: it's *your* photos, your
actual history, not a plausible facsimile of it.

## Decision

**mvideo's video and cover-art engines are deterministic: they assemble and
grade real media you supply (`ffmpeg` filter graphs over your photos/clips;
numpy/PIL band charts over the song's own energy for cover art). No frame,
shot, or cover image is model-generated by the core pipeline.**

Where this stops short of "never use AI at all": curation
(`assets/curation.py`) uses a cheap, explainable heuristic (hue/saturation/
brightness scoring against a station's palette) instead of a vision-model
call, on purpose — it's fast, free, deterministic, and good enough as a
*first sort a person then skims*, not a replacement for one. And cover art
is explicitly the one place a future AI-generation path is documented as
worth adding (see [ROADMAP.md](../ROADMAP.md)) — a single image is a single
generation call, not thousands, so the cost argument above doesn't apply
there the way it does to video.

## Consequences

**Good**

- Fast and cheap by construction: the bundled demo (24s, 28 cuts, 720p)
  renders in ~2 minutes end to end on a single core, with no API key, no
  network call, and no per-frame cost that scales with video length beyond
  ffmpeg's own encode time.
- The output is always *your* media. Re-running with the same brief and
  assets produces the same edit (seeded shuffling — see
  `timeline/compose.py`), which is what makes the cheap re-render story in
  [ADR-0001](0001-version-the-brief-not-the-render.md) possible at all: a
  generative model call is not reproducible the same way.
- No dependency on any external API's availability, pricing, or content
  policy for the core path to work.

**Bad, and accepted**

- You need media. This tool has nothing to say to someone with a song and no
  photos or footage of their own — `mvideo auto` still requires a
  `media_dir` argument. A stock-footage or generative fallback for that case
  is explicitly out of scope for now (ROADMAP.md).
- The visual vocabulary is what `render/effects.py` implements (cuts, zoom,
  kaleidoscope, strobe, grain, scanlines, halation, vignette, duotone,
  freeze). It's a real but finite palette, not "anything you can describe."

## What would overturn this

- If cover-art or caption generation via a real model call turns out cheap
  and controllable enough to be a *default*, not an opt-in extension, this
  ADR's boundary should move — but the video-assembly half of the argument
  (cost scales with length; a generated video isn't *your* footage) would
  need its own, separate reconsideration.
